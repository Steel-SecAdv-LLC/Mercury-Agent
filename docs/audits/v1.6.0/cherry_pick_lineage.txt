### #1 — ``three_r_mechanism.py`` sph_harm wrapper consistency

    modern   sph_harm_y (n, m, θ_pol, φ_az)    physics convention

The original wrapper was numerically correct (the wrapper-internal name
``phi`` was bound to the caller's azimuthal angle on both branches; the
underlying call order differed only because the underlying signatures
differ).  The branches were genuinely confusing to read, however, and a
"tidy-up" of either branch could silently desync the math across SciPy
releases.

Fix: rewrite the inline doc-comment to state the contract explicitly,
and pin the cross-version equivalence with
``tests/core/test_three_r_sph_harm_compat.py`` — five parametrised cases
plus a closed-form Y_0^0 / Y_1^0 check that catches polar/azimuthal

### #2 — ``MemoryVectorizer`` ignored constructor ``seed=``
``MemoryVectorizer.__init__`` accepted ``seed`` and stored ``self._rng``,
but ``_project_to_dim`` hard-coded ``np.random.default_rng(42)`` so the
constructor seed was silently ignored.  Misleading API.

the seed integer rather than a Generator state, because the projection
matrix must be REGENERATED identically on every call — using a

a different matrix per call, breaking the projection identity).
``_project_to_dim`` now derives a fresh ``default_rng(self._projection_seed)``
on each call, so the user-supplied ``seed`` actually controls the
projection identity.  Same default ``seed=42`` for backwards
compatibility with the previous ``np.random.seed(42)`` global call.

``MCDropoutWrapper`` accepted ``seed`` and stored ``self._rng`` from
the original RNG-cure pass, but the class performs no NumPy-based
perturbation — MC-Dropout sampling is driven entirely by
``torch.nn.Dropout`` stochasticity.  Dead state, misleading parameter.

Fix: remove ``seed`` and ``self._rng`` from ``MCDropoutWrapper.__init__``;
